A slice is a use case: every application gets exactly the documents it should see, gated by quality, freshness, and sensitivity. These are the four patterns teams build, each with runnable cookbooks.

## RAG and Agent Knowledge

Every RAG pipeline and agent depends on the knowledge it retrieves from, and raw document dumps fail it in predictable ways: duplicates crowd the top-k, stale versions contradict current ones, similarity surfaces chunks from the wrong documents, and nothing scopes what each application may know. None of these are similarity problems. They are metadata problems, and solving them is what makes a document set AI-ready.

| Layer | Raw document dump | With Deasy Labs |
| :-- | :-- | :-- |
| **Curation** | Drafts, copies, and expired content all indexed | Duplicates and superseded versions excluded by the quality gate |
| **Enrichment** | A chunk is anonymous text | Every chunk carries its document's tags |
| **Scoping** | One pool for every application | One slice per chatbot or agent, with its own rules |
| **Retrieval** | Similarity only | Metadata narrows the pool first, similarity ranks within it |
| **Over time** | The index rots | Freshness rules and scheduled workflows keep it current |

Curation alone pays for itself: in internal benchmarks, indexing only the latest version of each document improved retrieval accuracy by 46% relative to indexing everything.

## Compliance and Sensitive Data

The platform's built-in classifiers detect PII, PHI, and PCI at scale, roll the findings up into rule tags, and route flagged documents to a restricted review path with an auditable metadata trail. Customer-facing AI systems retrieve only from the clean slice; sensitivity is an opt-in gate chosen per use case.
